# 강화학습 설계 방안

## 목표
Policy 실행 중 인간이 개입할 수 있는 시스템을 구축하고, 이를 강화학습에 활용한다.

---

## 전체 아키텍처

```
[Policy 실행]
    ↓ observation 수집
[Supervisor 노드]  ←── Quest trigger 감지
    ↓ teleop 개입 시 즉시 전환 (인간 우선)
[Controller]
    ↓
[로봇 실행]

[Recorder] ← 항상 (obs, action, reward, is_intervention) 기록
```

---

## 데이터셋 구조 (기존 + 추가)

기존 LeRobot 포맷에 아래 컬럼 추가:

```
observation.state           (16,)  — joint positions
observation.images.*               — 카메라
action                      (16,)  — 실제 실행된 action (teleop or policy)
is_intervention             bool   — 인간 개입 여부 (핵심 라벨)
reward                      float  — 보상 신호 (설계 미정)
```

`is_intervention=True` : 인간이 teleop으로 제어한 구간
`is_intervention=False`: policy가 자율 실행한 구간

---

## Supervisor 노드 설계

### 상태 머신 (State Machine)

```
         trigger 눌림                  trigger 뗌 + 보간 완료
POLICY ──────────────→ INTERVENTION ──────────────────────→ RETURNING
  ↑                                                              │
  └──────────────────────────────────────────────────────────────┘
                      policy 정상 실행 재개
```

총 3가지 상태:
- **POLICY**: policy가 자율 실행 중
- **INTERVENTION**: 인간이 teleop으로 제어 중
- **RETURNING**: 인간이 trigger 뗀 후 policy로 복귀하는 보간 구간

---

### Phase 1: POLICY 상태 (정상 실행)

```
매 프레임 (30Hz):
  1. observation 수집 (카메라 + joint states)
  2. policy.select_action(obs) → policy_action 계산
  3. policy_action → controller publish
  4. 데이터셋 기록: (obs, policy_action, is_intervention=False)
  5. trigger 감지 → 눌리면 즉시 INTERVENTION으로 전환
```

- policy는 매 프레임 action을 계산하고 실행
- trigger 감지는 매 프레임 체크 (latency 최소화)

---

### Phase 2: POLICY → INTERVENTION 전환 (즉시, 1프레임)

```
trigger 눌린 순간:
  1. policy 계산 중단 (또는 계속 계산하되 결과 버림)
  2. teleop 명령을 controller로 즉시 전달
  3. 상태 = INTERVENTION
  4. intervention_start_time 기록
```

**인간이 최우선** — 지연 없이 즉시 전환. 보간 없음.
policy가 어떤 action을 계산 중이었든 상관없이 버림.

---

### Phase 3: INTERVENTION 상태 (인간 제어)

```
매 프레임:
  1. observation 수집 (동일하게 계속)
  2. teleop action (Quest) → controller publish
  3. 데이터셋 기록: (obs, teleop_action, is_intervention=True)
  4. trigger 감지 → 떼면 RETURNING으로 전환
```

- policy는 이 구간 동안 내부적으로 계속 돌아도 되고, 아예 멈춰도 됨
  - 계속 돌리는 쪽이 복귀 시 첫 action 품질이 더 좋을 수 있음
  - 단 observation이 teleop으로 바뀐 상태이므로 policy 내부 상태는 어차피 리셋 필요

---

### Phase 4: INTERVENTION → RETURNING 전환

```
trigger 뗀 순간:
  1. policy.reset() 호출 → action chunk 버퍼 초기화
  2. 현재 joint 상태(q_current) 읽기
  3. policy 첫 action 계산 → q_target
  4. |q_target - q_current| 거리 계산
  5. 거리에 비례한 보간 프레임 수 결정 (N프레임)
  6. 상태 = RETURNING
```

**왜 policy.reset()이 필요한가:**
ACT 같은 action chunking policy는 내부에 과거 observation 히스토리와
미래 action 청크를 캐싱하고 있음. 인간이 개입한 동안 로봇 위치가 바뀌었기 때문에
이 캐시가 현재 상태와 맞지 않음 → reset 없이 복귀하면 policy가 엉뚱한 곳에서 시작.

---

### Phase 5: RETURNING 상태 (보간 복귀)

```
매 프레임 (총 N프레임):
  alpha = frame_index / N  (0.0 → 1.0)
  q_interp = (1 - alpha) * q_current + alpha * q_policy_first
  q_interp → controller publish
  데이터셋 기록: (obs, q_interp, is_intervention=False)
  frame_index += 1

N프레임 완료 → 상태 = POLICY (정상 복귀)
```

**보간 프레임 수 N 결정 기준:**
```
max_joint_diff = max(|q_target - q_current|)  # 가장 많이 움직여야 하는 관절
N = max_joint_diff / max_speed_per_frame       # 속도 제한 기준으로 계산
N = clamp(N, min=5, max=30)                    # 최소 5프레임, 최대 1초(30Hz)
```

RETURNING 구간 중 다시 trigger 눌리면 → 즉시 INTERVENTION으로 재전환.

---

### 전체 흐름 타임라인 예시

```
시간 →
────────────────────────────────────────────────────────────────
  POLICY   │ INTERVENTION (인간 제어)  │ RETURNING │  POLICY
────────────────────────────────────────────────────────────────
is_interv: False                True              False    False
action:    policy            teleop           interp   policy
────────────────────────────────────────────────────────────────
           ↑                  ↑                ↑         ↑
        trigger 눌림      trigger 뗌       보간 완료   정상 실행
```

---

### 데이터 품질 관련

- **RETURNING 구간 데이터**: 보간값이라 실제 인간 의도도 policy 의도도 아님
  - `is_intervention=False`로 기록하되, 학습 시 이 구간을 제외하거나 낮은 weight 부여 고려
  - 별도 `is_returning` 컬럼 추가도 가능
- **INTERVENTION 직전 POLICY 구간**: policy가 실패하던 구간 → 낮은 보상 부여 예정
- **INTERVENTION 구간**: 인간 정답 데이터 → 높은 보상 또는 높은 학습 weight

## 강화학습 활용 방식

### 데이터 수집 전략
- Policy 실행 중에도 계속 데이터셋 축적
- 인간 개입 구간도 동일 포맷으로 기록
- `is_intervention` 라벨로 구분

### 학습 알고리즘 후보

| 방법 | 설명 | 적합도 |
|------|------|--------|
| **IQL / AWAC** | 오프라인 RL, 현재 구조에 가장 잘 맞음 | ★★★ |
| **IWR (Intervention-Weighted Regression)** | `is_intervention=True` 샘플에 높은 loss weight | ★★★ |
| **DAgger** | 개입 구간 데이터만 기존 dataset에 추가 후 재학습 | ★★☆ |
| **Online fine-tuning** | 빠르지만 실제 로봇에 위험 | ★☆☆ |

## 핵심 미결 사항

### 1. 보상 설계 (가장 중요)
아직 결정되지 않음. 후보:
- **에피소드 끝 인간 평가** (성공/실패 스칼라) → sparse하지만 정확
- **실시간 자동 보상** (비전 기반, 거리 기반 등) → dense하지만 설계 복잡
- **인간 개입 빈도 역수** → 개입이 적을수록 높은 보상

### 2. 학습 알고리즘 확정
보상 설계에 따라 달라짐. 미결.

### 3. 재학습 시점
몇 에피소드마다 fine-tune할지 미결.

## 구현 순서 (예정)

1. `inference.py` + `collect_data.py` 통합 (rollout 중 데이터 수집)
2. Supervisor 노드 구현 (teleop/policy 전환 + 기록)
3. `is_intervention` 컬럼 dataset에 추가
4. 보상 설계 확정 후 `reward` 컬럼 추가
5. RL 알고리즘 적용
